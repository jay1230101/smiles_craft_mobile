Smile Craft Mobile

Milestone 3 — Delivery Summary (revised 15 June 2026)

Project: Smile Craft mobile app
Platforms: iOS & Android
Milestone: M3 — Patient Records, Appointment Actions & Clinical Workflow
Build: v1.2.0
Status: Delivered

1. What this milestone covers

Milestone 3 turns the app from a read-only schedule viewer into a working clinic tool. Clinic staff can now register new patients, cancel and reschedule appointments from a tap-and-act popover on the calendar, manage their account from a proper profile screen, and review a live notifications feed of everything happening in the clinic.

Following the 11 June process-flow review, three additional actions from the appointment popover were brought into M3: Treatment & Orders, New Plan of Care, and Schedule Future WhatsApp. The Edit / Reschedule screen was also rebuilt to match the web behavior — including Search Patients (patient swap on an existing booking), a Notes field, and Delete Appointment. A dedicated Clinical History screen was added so a clinician can review past visits and prior plans of care for the patient in one tap from the popover.

2. Features delivered

2.1 Patient Registration Live
  • New-patient form on the Register tab with first name, family name, date of birth, phone, gender, assigned doctor, email, and allergies/notes. (Father's Name field removed in v1.2.0 per client request — the backend still accepts the column, it's just not collected from mobile.)
  • Built-in validation: required-field checks, date-of-birth is auto-masked to DD-MM-YYYY and rejected if not a real past date, phone is digits-only, email is checked for the right format.
  • Duplicate detection: if the phone is already registered to another patient, the app surfaces a confirm dialog showing the existing patient's name and gives the user the choice to continue anyway or cancel.
  • Role-aware doctor selection: non-owner doctors can only register patients under their own name (the field is locked); owners, assistants, and admins pick from a doctor list.
  • Wired to the existing POST /register-patient backend; gender list pulled live from GET /getGender.
2.2 Calendar Appointment Popover Live

Tapping a booked appointment on the Day or Week view opens a popover with patient name, status, time range, treatment, and doctor. The action set mirrors the web app:

  • Orders — opens the Treatment & Orders screen (see 2.3).
  • New Plan of Care — opens the Plan of Care screen (see 2.4).
  • Schedule Future WhatsApp — opens the WhatsApp scheduler (see 2.5).
  • Edit / Reschedule — opens the rebuilt edit form (see 2.6).
  • Clinical history — opens the patient's Visits + Plan of Care history (see 2.7).
  • Cancel appointment — reason picker loaded live from GET /cancellation-reasons; submits to POST /cancel-appt. Already-cancelled appointments show this action greyed out with helper text.
  • Confirm appointment — shown as a placeholder action. Needs a small backend addition (see Section 4) before it can be wired.
2.3 Treatment & Orders Live

Reached from the popover's "Orders" action — the mobile equivalent of the web Orders modal.

  • Procedure picker with auto-fill price — selecting a procedure populates the Price field from the clinic's procedure catalog, matching the web behavior.
  • Tooth number field shown only when the clinic has tooth tracking enabled (driven by the same flag the web uses).
  • Status picker (e.g. In Process / Completed / Not Done) — defaults to the clinic's default status.
  • Staged procedures table — lets the clinician add multiple procedures before submitting, identical to the "waiting validation" table on web.
  • Pending procedures table — horizontally scrollable list of in-process procedures for this patient + doctor, with a per-row status-update selector for moving items to Completed or Not Done.
  • One Save call posts new procedures and any per-row status updates together through the existing POST /treatment-plan route (same backend the web uses).
2.4 New Plan of Care Live
  • Reached from the popover's "New Plan of Care" action.
  • Treatment Notes multi-line text area with a live xxx / 1000 character counter (1000-char cap matches the web).
  • Quick Templates pill row — Crown · RCT · Implant · Cleaning — tapping a template inserts the same standardized note text the web uses, so a clinician can drop in a baseline plan and edit on top.
  • Save posts to POST /planOfCare; the note then appears in this patient's Clinical History (Plan of Care tab).
2.5 Schedule Future WhatsApp Live
  • Reached from the popover's "Schedule Future WhatsApp" action.
  • Template picker loaded live from GET /getActiveTemplates (only the clinic's active WhatsApp templates show up).
  • Date picker bounded between tomorrow and +3 years out, so a clinician cannot accidentally schedule a same-day or far-future reminder.
  • Save posts to POST /store_reminders with the chosen template + date for that patient. The patient will receive the WhatsApp message on the scheduled date via the existing Celery + WhatsApp pipeline.
2.6 Edit / Reschedule Appointment Live

Rebuilt to match the web "Booking Appointment" dialog. Reached from the popover's "Edit / Reschedule" action.

  • Register Patient shortcut at the top opens the New Registration modal, so a clinician who realizes the booking is for a brand-new patient can register them inline without losing the edit context.
  • Search Patients input at the top — typing two or more characters triggers a debounced fuzzy search against POST /search-patient (name / family / phone). Tapping a result swaps the patient on this booking; a "Swapped — undo" badge appears next to the patient block until the user reverts. Useful when the wrong patient was originally selected.
  • Patient block shows Name, Family, and DOB read-only (from the active patient — the swap or the original) so the clinician always sees who they are saving against.
  • Schedule block — editable Date (DD-MM-YYYY), Start, and End (HH:MM). End must be after Start; validated as the user types.
  • Notes textarea — replaces the old single-line "Treatment" field. Saves to the same proc field the web uses.
  • Doctor displayed read-only as "Dr. <name>" — the assigned doctor is fixed at booking time, same as the web.
  • WhatsApp reminder checkbox preserved.
  • Delete appointment — full-width red button at the bottom opens a confirmation dialog ("Delete this appointment? Keep it / Delete"). On confirm, posts { eventToDelete } to POST /encounter — the same dual-purpose route the web uses for cancel-and-delete.
  • Save and Delete both refresh the calendar, dashboard, and notifications feed automatically.
2.7 Clinical History Live
  • Reached from the popover's "Clinical history" action.
  • Two-tab pill control at the top: Visits and Plan of Care.
  • Visits tab lists past visits for this patient (date, doctor, procedure, status), backed by GET /getVisitsHistory.
  • Plan of Care tab lists prior plan-of-care entries with date, author, and the full note text, backed by GET /get-plan-care.
  • Both lists are read-only — editing is done in their respective modals (Orders and New Plan of Care).
2.8 Profile & Settings Live
  • New profile screen reached from the avatar button in the Dashboard header (replaces the interim Logout button that was sitting on the dashboard since M2).
  • User card with avatar (auto-initials), name, role (pretty-printed: "Owner Doctor", "Assistant", etc.), and email.
  • Preferences section with Language and Push Notifications listed as roadmap items (push needs a backend update — see Section 4).
  • About section with the app version, build number, and clinic ID.
  • Log out button with a confirmation dialog before signing out.
2.9 Notifications Inbox Live
  • New Notifications screen reached from the bell button on the Dashboard.
  • Captures every appointment and patient change that arrives in real time over the existing socket connection (new bookings, updates, confirmations, cancellations, deletions, patient registrations, edits, removals).
  • Each entry has a kind-aware icon and tint, the headline of what changed, who it relates to, and a relative timestamp ("Just now", "5m ago", "3h ago", etc.).
  • The Dashboard bell shows a red dot as long as there are unread notifications.
  • Mark all as read and Clear all actions; the inbox keeps the 100 most recent items.
  • This is a client-side feed; a server-backed inbox would land later if the team wants notifications to persist across devices or app reinstalls.

3. Technical notes

  • All M3 screens — including the four amendment additions (Orders, Plan of Care, Future WhatsApp, Clinical History) — are fully wired to the existing live backend. No new backend services were stood up; the mobile app uses the same APIs the web app already uses.
  • One unified backend route per concern: /treatment-plan handles new procedures + status updates in a single call; /encounter handles edit and delete via its payload; /search-patient drives both the Edit screen's patient swap and the patient list search. The mobile app maps 1-to-1 to these routes, so there is no second source of truth to maintain.
  • Demo mode (which the QA tester uses by default) returns realistic fake responses so every flow can be exercised without hitting the live system. Switching from demo to live is a one-line flag.
  • Forms use React Hook Form + Zod (same stack as the M2 login and forgot-password forms) for consistent validation and a single way to maintain forms going forward.
  • The doctor picker added in the M2 polish round is reused throughout M3 — same selection control on Calendar, Dashboard, Registration, and Edit screens.

4. Backend updates needed for the next milestone

Two small backend additions would close the remaining placeholders shown in the popover:

  • Manual confirm appointment endpoint — today the only way an appointment moves to "confirmed" is through the WhatsApp webhook (patient taps Confirm in WhatsApp). The mobile app needs:
    POST /confirm-appt  { bookingId }  →  sets patient_confirmed = True and emits confirmedAppointment on the same rooms the existing flow uses.
  • Push notification device-token registration — needed before iOS/Android push notifications can be turned on:
    POST /register-device-token  { token, platform }  →  stores per-user, then the existing socket emits should call a Celery task that pushes to those tokens via FCM / APNs.
